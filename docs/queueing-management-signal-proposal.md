# 대기행렬 기반 질문 대응 여유 신호 제안

> **상태: 상담 질문을 위한 근거 문서 — 계산 신호·공개 카드는 Stage 1 학부모 검증 이후.**
>
> 이 문서는 사용자가 제공한 과제 논문을 바탕으로, 학원콕이 반 정원·강사 배치·질문 대응 구조를 **상담 질문의 설명과 생성에 활용**하는 방법을 기록한다. 이 모형은 제품의 핵심 추천 기준이나 품질 평가 체계를 정의하지 않는다. 현재 `data/academies/*.json` 사실 정본, 추천 API 계약 또는 공개 랭킹은 변경하지 않는다. 제품 정의·데이터 경계·검증 순서의 공식 결정은 [2026-09-01 의사결정 기록](decision-log.md)과 [2026-08-21 MVP 재정의](decision-log.md)를 따른다.
>
> `POST /consultation/questions` 계약은 2026-08-30에 이미 고정됐다. 이 문서의 다음 단계는 질문 축을 학부모 검증하는 것이지, 새 추천 API를 만드는 것이 아니다.

## Objective

학부모가 출처 있는 후보 정보를 검토하는 과정에서, 등록 전 상담과 재원 중 점검을 통해 **학생의 질문이 실제로 제때 처리될 수 있는 수업 구조인지** 확인하도록 돕는다. 목표는 “좋은 학원” 또는 “가성비 좋은 학원”을 판정하는 것이 아니라, 공개·확인된 운영 정보와 학부모의 확인을 바탕으로 **질문 대응 여유**, **확인해야 할 운영 조건**, **미확인 정보**를 투명하게 보여 주는 것이다.

이 방향은 학원콕의 제품 정의와 일치한다. 학원콕은 학부모가 학원·학습 상태의 블랙박스를 줄이고 더 나은 질문과 판단을 하도록 돕는 서비스이며, 검증되지 않은 수업 방식이나 관리 수준은 평가가 아닌 `상담에서 확인할 점`으로 다뤄야 한다([제품 원칙](../AGENTS.md), [데이터 전략](data-strategy.md)).

## 논문에서 확인한 핵심 모형

사용자 제공 논문 *Determining Optimal Class Size in a Private Academy Using Queuing Theory*는 수학학원 수업 중 학생 질문을 대기행렬로 모델링했다.[^paper] 한 명의 강사가 질문을 처리하는 경우를 M/M/1, 보조강사가 함께 질문을 처리하는 경우를 M/M/2로 분석했다.

| 논문 변수 | 의미 | 논문 내 설정 |
|---|---|---|
| `N` | 반의 학생 수 | 6~15명 시나리오 |
| `T` | 실제 질의응답 가능 시간 | 130분 수업 중 100분 |
| `q` | 학생 1인당 평균 질문 수 | 4개/수업 |
| `λ` | 질문 도착률 | `N × q / T` |
| `μ` | 강사 1인당 질문 처리율 | 0.40 질문/분 |
| `c` | 동시에 질문을 받는 강사 수 | 1명(M/M/1), 2명(M/M/2) |
| `ρ` | 강사 가동률 | M/M/1: `λ / μ`, M/M/c: `λ / (c × μ)` |

논문은 `ρ ≤ 0.7`을 안정 운영의 경계로 두었다. 해당 사례의 관측 가정에서는 단일 강사일 때 7명, 보조강사가 함께 질문을 처리할 때 14명이 경계 안에 있었다. 이는 **특정 학원·과목·수업 방식에 일반화할 수 있는 적정 정원 숫자**가 아니라, 질문 수요와 응답 공급의 균형을 보여 주는 사례다.

## 학원콕 적용 판단

### 결론: ‘학원 평가 점수’가 아니라 ‘질문 대응 여유 신호’로는 높은 활용 가치가 있다

반 정원만 보는 것은 불완전하다. 같은 10명 반도 실제로 질문을 받는 강사 수, 강사의 질문 처리 시간, 보조강사의 역할, 자습·문제풀이 시간, 학생의 학습 수준 혼합도에 따라 전혀 다른 경험이 될 수 있다. 대기행렬 관점은 이 문제를 `반 정원`이 아닌 **질문 수요 대 응답 가능 공급**으로 바꾼다.

| 적용 방식 | 적합성 | 이유 |
|---|---:|---|
| 학원 종합 별점 또는 순위 반영 | 부적합 | 관측 가정에 민감하고, 학원·학생의 교육 품질을 단정하게 됨 |
| AI 추천 점수에 직접 가산 | 초기에는 부적합 | 현재 추천 점수는 응답 내 상대 순위이며, 운영값의 결측·비교 불가능성이 큼 |
| 후보 상세의 ‘질문 대응 구조’ 카드 | 적합 | 입력값·출처·확인일·미확인 항목을 함께 투명하게 제시 가능 |
| 상담 질문 생성 | 매우 적합 | 값이 없을 때도 사용자가 정확한 질문을 하게 해 즉시 가치 제공 |
| 등록 후 ‘상담 약속 이행’ 점검 | 매우 적합 | 실제 대기·클리닉·보조강사 투입을 월별로 확인할 수 있음 |
| 학원 운영자용 정원·보조강사 시뮬레이터 | 후속 검증 후보 | 학원에 관리 역량을 증명할 도구가 될 수 있으나 B2B 수요 검증이 선행돼야 함 |

## 제품 표현 원칙

공개 화면의 명칭은 **‘질문 대응 여유’**, **‘질문·오답 관리 확인’**처럼 사용한다. ‘교육비 대비 점수’, ‘교육 품질 점수’, ‘최적 반 정원’, ‘학원 등급’은 사용하지 않는다. 수치가 있더라도 그것은 관측 기간과 가정을 가진 운영 시뮬레이션일 뿐, 학생 성과나 학원의 총체적 품질을 증명하지 못한다.

| 상태 | 사용자 화면 표현 | 필요한 근거 |
|---|---|---|
| 충분한 입력값과 최근 확인 | `질문 대응 여유: 확인된 운영 정보 기준으로 점검 가능` | 반별 실제 인원·동시 질문 대응 인력·질의응답 시간·관측일 |
| 일부 입력값만 있음 | `반 정원은 확인됨 — 질문 대응 인력·클리닉 시간은 상담에서 확인하세요` | 최소 한 개의 출처 있는 사실 |
| 입력값 없음 | `질문 대응 구조 미확인` + 맞춤 질문 | 출처 없는 추정을 하지 않음 |
| 등록 후 개인 기록 | `이번 달 확인한 운영 경험` | 학부모가 직접 기록한 기간·응답, 사실 DB와 분리 |

## 필요한 입력값과 계산 경계

### 1. 최소 입력값

반드시 **과목·학년군·수업반·수업 시간대 단위**로 받아야 한다. 학원 전체 강사 수나 전체 등록 학생 수만으로는 특정 반의 질문 대응 여유를 계산할 수 없다.

| 필드 | 설명 | 출처 수준 |
|---|---|---|
| 평균 실제 출석 인원 `N` | 정원이 아닌 최근 4주 평균 실제 인원 | 학원 확인 또는 반복 관측 |
| 수업 중 질문 가능 시간 `T` | 강의·시험을 제외하고 강사가 개인 질문을 받는 시간 | 시간표·상담 답변 |
| 동시 질문 대응 인력 `c` | 해당 반·해당 시간에 실제 질문을 받을 수 있는 강사/보조강사 수 | 역할까지 명시한 상담 답변 |
| 1인당 질문 수 `q` | 대표 주차의 평균 또는 구간값 | 초기에는 학부모 관찰·자기기입이 적합 |
| 평균 1건 처리 시간 `1/μ` | 단순 확인, 풀이 설명, 오답 재설명 등을 포함한 평균 | 표본 관찰 또는 학원 운영 로그 |
| 관측 기간·확인일 | 계산값의 최신성·재현성 확보 | 모든 입력값에 필수 |

### 2. 계산과 표기

초기에는 계산값을 사용자에게 노출하지 않고, 다음 상태만 제시하는 편이 안전하다.

| 내부 신호 | 조건의 예시 | 사용자용 표현 |
|---|---|---|
| 여유 | `ρ`가 사전 정의한 보수적 기준 안에 있고, 입력값이 최근 확인됨 | `질문 대응 여유를 확인할 수 있어요` |
| 경계 | 기준에 가깝거나 일부 값의 신뢰도가 낮음 | `질문이 몰리는 시간의 운영을 더 확인해 보세요` |
| 부담 가능성 | 기준을 초과했거나 실제 대기 경험이 반복 확인됨 | `질문 대기·클리닉 운영을 꼭 확인해 보세요` |
| 미확인 | 최소 입력값 부재 | `현재 공개 정보만으로는 판단할 수 없어요` |

`ρ ≤ 0.7`은 사용자 논문의 사례 가정이며 제품의 보편적 합격선으로 고정하지 않는다. 실제 제품에서는 과목·수업 형식별 실측 데이터가 축적된 뒤에만 내부 기준 후보로 검토한다. 초기 상담 질문은 숫자 계산 없이도 동작해야 한다.

## 상담 질문 도우미 적용안

사용자가 ‘반이 12명이고 강사는 한 명’처럼 일부 정보를 입력하면, 빈 값을 채우도록 유도하는 질문을 생성한다.

| 확인하려는 것 | 상담 질문 예시 |
|---|---|
| 실제 반 인원 | `정원이 아니라 최근 수업의 실제 출석 인원은 보통 몇 명인가요?` |
| 질문 대응 인력 | `문제풀이 시간에 학생 질문을 동시에 받는 선생님은 몇 분인가요? 보조강사도 풀이 설명을 해주시나요?` |
| 질문 가능 시간 | `130분 수업 중 강의·시험을 제외하고 개별 질문이나 오답 설명을 받는 시간은 평균 몇 분인가요?` |
| 피크 시간 대응 | `숙제 검사나 문제풀이가 끝나는 시간에 질문이 몰리면, 평균 얼마나 기다리며 어떤 순서로 도움을 받나요?` |
| 클리닉 제공 | `월별 클리닉·보강은 정규 수업과 별도로 몇 회·몇 분 제공되며, 실제 참여 기준은 무엇인가요?` |
| 약속 이행 확인 | `등록 후 첫 한 달 동안 반 인원·보조강사·오답 관리가 상담에서 들은 방식과 같은지 어떻게 확인할 수 있나요?` |

## 등록 후 점검안

등록 후에는 학생·학부모가 한 달에 한 번, 짧은 구조화 입력으로 상담 약속과 실제 경험을 비교한다. 자유 서술·성적표·실명 수집은 기본 흐름에 넣지 않는다.

| 확인 항목 | 입력 예시 | 비교 기준 |
|---|---|---|
| 실제 반 인원 | `최근 4주 평균 10명` | 상담 시 안내 인원 또는 정원 |
| 질문 대기 체감 | `대부분 5분 이내 / 가끔 오래 기다림 / 자주 기다림` | 절대 점수화하지 않고 월별 추이 |
| 보조강사 투입 | `매주 있음 / 일부 수업만 / 없음 / 모름` | 상담 시 안내 여부 |
| 오답·클리닉 | `주 1회 / 월 2회 / 필요 시 / 모름` | 상담 시 안내 횟수·조건 |
| 학부모 피드백 | `월간 리포트 있음 / 문의 시 응답 / 없음 / 모름` | 상담 시 안내 주기 |

이 기록은 학원 사실 DB와 엄격히 분리한 개인 점검 데이터 또는 브라우저 로컬 상태로 다룬다. 초기 MVP에서는 비로그인·비저장으로도 충분하며, 반복 사용 수요가 확인된 뒤에만 선택형 저장을 검토한다.

## 데이터·아키텍처 권고

현재 `academies`는 검증된 사실 테이블이고 `teacher_count`와 `classroom_count`만 nullable 필드로 존재한다. 대기행렬 계산에 필요한 값은 학원 전체 값이 아니라 반·과목·시간대별 운영값이며, 추론과 최신성이 중요하다. 따라서 `data/academies/*.json`에 ‘질문 대응 점수’나 계산 결과를 넣지 않는다.

향후 실험을 진행한다면, 사실 테이블과 분리된 `academy_operation_profiles` 또는 `academy_management_signals` 계층을 고려한다. 각 레코드는 `academy_id`, `course_scope`, `observed_at`, `source_type`, `source_url_or_note`, `actual_class_size`, `qna_minutes`, `simultaneous_response_staff`, `question_rate_band`, `service_time_band`, `calculation_version`, `confidence/status`를 가진다. 원시 학부모 서술은 저장하지 않고, 사용자에게는 입력값·관측 시점·미확인 사항만 보여 준다.

현재 공개 API의 `score`는 같은 응답 안에서만 비교하는 상대 순위이며 별점·퍼센트·신뢰도로 표시하면 안 된다. 이 신호를 기존 `POST /recommendations/ai` 점수에 넣거나, 사실 데이터 필터로 만들지 않는다. 후속 실험에서 표시 수요·신뢰성·업데이트 운영이 검증된 뒤에만 별도 투명성 필드와 계약 변경을 검토한다.

## 검증 순서

| 순서 | 목표 | 성공 신호 | 중단 또는 보류 조건 |
|---:|---|---|---|
| 1 | 상담 질문 유용성 검증 | 5~10명의 학부모가 질문을 실제 상담에 사용하고, 빠진 질문을 제시함 | 수치 설명이 질문보다 혼란을 키움 |
| 2 | 구조화 답변 수집 가능성 검증 | 10~20개 반에서 최소 입력값을 출처와 함께 확보 | 학원이 평균 반 인원·질문 인력 공개를 거부하거나 값이 모호함 |
| 3 | 등록 후 체감과의 보정 | 대기 체감·클리닉 이행과 신호가 일관되게 연결됨 | 모델 경계와 실제 경험의 불일치가 반복됨 |
| 4 | 공개 노출 실험 | 사용자가 카드의 `미확인`과 `상담 질문`을 이해하고 행동함 | 학원 평점·추천 순위로 오해하는 비율이 높음 |
| 5 | 이후에만 | 학원 운영자용 시뮬레이터 또는 강화 프로필 수요 검증 | 지불 여부가 일반 후보 순위에 영향을 주는 구조가 됨 |

## Recommendation

1. **상담 질문의 축으로 검증한다.** 명칭은 ‘적정 반 정원 지표’가 아니라 **질문 대응 여유 신호**로 한다.
2. **첫 구현은 계산기가 아니라 질문 도우미다.** 객관적 후보 탐색 결과를 상담과 비교 판단으로 잇는 Stage 1 경험에 결합한다.
3. **추천 점수·학원 순위에는 넣지 않는다.** 결측치와 가정 민감성이 높은 운영 신호이므로 후보 상세의 투명성 카드와 등록 후 점검에 한정한다.
4. **수치 기준은 실측 보정 후에만 쓴다.** 논문 속 `ρ ≤ 0.7`은 제품 정책이 아니라 사례의 가정으로 남긴다.
5. **데이터는 반 단위·관측일 단위·출처 단위로 분리 관리한다.** 학원 전체 강사 수와 반 정원만으로 서비스 품질을 추정하지 않는다.

## Next Step

객관적 학원 정보의 범위·최신성을 계속 보강하는 동시에, `질문 대응·오답 관리` 축의 상담 질문을 기존 체크리스트/`POST /consultation/questions` 흐름에 넣고 5~10명 학부모 인터뷰로 단어·질문 순서·혼란 지점을 검증한다. 이후 공개 리뷰 탐색을 통해 주관적 경험을 출처·시점·한계와 함께 제공하는 신뢰성·유용성을 확인한다. 이 두 단계가 검증된 뒤에만 반 단위 운영 프로필 수집과 계산 카드의 프로토타입을 검토한다.
