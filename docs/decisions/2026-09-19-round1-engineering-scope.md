## 결정

코드 작업은 아래 세 가지로 한정한다. 점수·정렬·API 계약·수집 범위는 바꾸지 않는다.

1. **랜딩 학원 수에 출처·수집 기준일을 붙인다** (`landingFacts.ts`의
   `MISA_ACADEMY_COUNT_SOURCE`·`MISA_ACADEMY_COUNT_AS_OF`, 근거 섹션 문구). 기준일은
   `data/README.md`의 수집일과 같아야 하며 테스트가 대조한다.
2. **후보 카드에서 사실과 탐색 신호를 분리한다.** 채점은 등록 정보(`subjects`·
   `subject_detail`) 매치만 `subject`로, 이름에만 보이는 경우는 `subject_name`으로 낸다.
   가중치는 둘 다 `WEIGHT_SUBJECT`로 같아 **랭킹은 불변**이다. 컬럼이 비어 있으면
   `subject`는 `unknown`에 남는다. 카드는 "등록 정보와 맞는 조건"과 "학원 이름에서
   추정한 신호"를 다른 줄로 적고, 폴백 이유 문장은 이름 신호를 "등록 정보와 맞는"
   개수에 넣지 않는다. 프론트는 `CONDITION_LABELS`와 `SIGNAL_LABELS`를 갈라 두고 키가
   겹치지 않게 테스트로 지킨다.
3. **비식별 집계 수요 리포트 CLI**(`app.cli.demand_report`, 별도 PR)를 만든다.
   `search_history`·`click_logs`를 기간·학년군·과목·지역·행동 유형으로 집계하고, 최소
   표본 미만 셀은 억제하며 원문 질의는 출력하지 않는다. 2개월차 원장 리포트 **시안**의
   재료이지 판매 상품이 아니다.

Founder 결정(2026-09-19): 상담 요청 차원 로깅(새 테이블·마이그레이션)과 상담 질문에
"실제 반 인원·질문 대응 인력" 축을 추가하는 것은 이번 라운드에서 하지 않는다.

## 검토한 대안·트레이드오프

- **이름 매치 가중치를 낮추기**: 이름만 맞는 후보가 뒤로 밀려 더 정직해 보이지만 랭킹이
  바뀐다. 소프트 랭킹 재검토는 라벨 커버리지가 생긴 뒤 별도 결정(`docs/data-strategy.md`)
  이라 이번엔 키만 가른다.
- **이름만 맞을 때 `conflicts`에 넣기**: 지역검색 `category`로 채운 `subjects`는 불완전할 수
  있어 "조건과 다른 점"으로 단정하면 과잉 충돌이 된다. 넣지 않는다.
- **운영 DB `total`(411)을 런타임으로 표시**: 마운트 시 전체 fetch가 필요하고(2026-09-08
  금지) 기준일이 사라진다. 정적 상수 + 기준일을 유지한다.
- **상담 요청 차원 로깅**: 리포트에 "상담 확인 항목" 축이 생기지만 수집 범위가 늘고
  마이그레이션이 필요하다(Preview가 운영 DB를 공유). 보류.

## 바꾸지 않은 것

- 점수 가중치·정렬·후보 풀 상한·완화 사다리, `POST /recommendations`와
  `/recommendations/ai`의 분리, `score` 비표시
- `POST /consultation/questions` 계약·질문 문장·미저장
- 학원 사실 정본(Supabase Studio)·null 원칙, 공개 쓰기 API 없음
- `matched_conditions`·`unknown_conditions`·`conflicts` 투명성 필드 자체 (키 하나가 늘었을 뿐)

## 하지 않은 것

- 상담 요청 로깅, 상담 질문 축 추가, 로그인·저장·비교, 리포트 판매·결제, 인접 지역,
  `POST /chat`, 학원 사실 데이터 수정
