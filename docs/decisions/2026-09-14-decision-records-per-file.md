# 결정 기록을 결정 하나당 파일 하나로 남긴다

- 날짜: 2026-09-14
- 상태: 채택
- 대체: `decision-log.md` 2026-08-14 — GitHub를 다중 AI 협업 허브로 (AGENTS.md 도입, 느슨하게) 중
  "결정과 그 이유는 `docs/decision-log.md` 맨 위에 남긴다"는 기록 위치 규칙

## 계기

- `docs/decision-log.md`가 10주(2026-07-03~09-13) 만에 60항목·1600줄을 넘었다. 하루에 8항목이
  쌓인 날도 있다(2026-09-12). 에이전트가 한 번에 읽지 못하고 나눠 읽어야 한다.
- 모든 결정을 같은 파일 맨 위에 삽입해서, 병렬 브랜치가 같은 줄을 고친다. 실제로 이 파일의 충돌을
  손으로 풀었다(`de8835c merge: resolve decision-log conflict with main`). 이 저장소는 여러 AI·
  병렬 서브에이전트·Cloud Agent 브랜치가 동시에 결정을 남긴다.
- 어떤 결정이 대체됐는지가 "대체 대상"·"번복" 같은 산문 속에만 있어, 아직 유효한 결정을 한눈에
  가릴 수 없다.
- `docs/ai-team.md`의 템플릿(배경/결정/이유·트레이드오프/하지 않기로 한 것)과 실제로 쓰인 필드
  (계기·바꾸지 않은 것·결정·다음 순으로 많이 쓰임)가 달랐다.

## 결정

- 2026-09-14부터 새 결정은 `docs/decisions/YYYY-MM-DD-slug.md`에 하나씩 쓴다. 파일 이름·템플릿·
  대체 규칙은 [README](README.md) 한 곳이 정본이다.
- `docs/decision-log.md`는 경로와 내용을 그대로 두고 동결한다. 2026-09-13까지의 기록 보관용이며
  새 항목을 추가하지 않는다.
- 파일마다 `상태`·`대체` 줄을 둬서, 대체 관계를 산문이 아니라 메타데이터로 드러낸다.
- 템플릿의 핵심 절은 실제 사용 빈도를 따라 계기·결정 두 개로 두고, 나머지는 선택이다.
  `docs/ai-team.md`의 템플릿은 README를 가리키는 포인터로 바꿨다.

## 검토한 대안·트레이드오프

- **과거 항목도 전부 파일로 분할**: 형식은 통일되지만, 코드·문서의 날짜 참조 약 50줄을 새 경로로
  고쳐야 하고 같은 날 최대 8항목의 slug를 소급해 지어야 한다. 동결하면 기존 참조가 전부 그대로
  유효하다.
- **순번 파일명(MADR의 `0001-`)**: 병렬 브랜치가 같은 번호를 만든다. 날짜 파일명은 log4brains가
  같은 이유로 쓰는 방식이고, 기존 `YYYY-MM-DD` 참조 관례와도 같다.
- **메타데이터를 YAML front matter로**: 도구 연동에는 유리하지만 기존 항목과 모양이 다르다. 불릿
  줄은 기존 모양과 같고, log4brains가 읽는 MADR 2.x 불릿 형식과도 호환된다.
- **외부 도구 도입(log4brains·adr-tools, 에이전트 메모리 mem0·cognee 등)**: 지금 규모에서는 폴더
  목록과 grep으로 충분하다. 도구는 운영 비용만 늘린다.

## 바꾸지 않은 것

- `docs/decision-log.md`의 기존 항목 본문, 그리고 그 항목을 가리키는 코드·테스트·문서의 날짜 참조.
- `tests/test_app_explore_copy.py`의 `test_decision_log_records_expression_principles`(보관 로그를 읽는다).
- 결정권은 Founder에게 있고 AI는 선택지와 근거를 만든다는 역할 구조(`docs/ai-team.md`).

## 하지 않은 것

- spec-kit식 constitution 파일 — `AGENTS.md` §7과 같은 역할이라 정본이 둘이 된다.
- 결정 목차 파일 — 파일 이름이 날짜순이라 목록으로 충분하고, 목차는 이중 기록이 된다.
- 파일명·필수 절을 검사하는 테스트나 CI — 처음부터 강제하지 않는다.
