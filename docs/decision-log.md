# 의사결정 로그

주요 기술적/제품적 의사결정과 그 이유를 기록한다.

## 2026-08-27 — 객관적 학원 정보 기반 추천에 상담 보조 AI와 리뷰 근거를 결합

- **계기**: 학원콕은 처음부터 출처와 확인일이 있는 객관적 학원 정보를 바탕으로 후보를 탐색·추천하는 서비스였다. 당근 광고 반응에서 ‘지불한 비용에 비해 상담과 학습 관리가 충분한가’라는 문제의식에 반응이 나타나, 추천 결과를 실제 선택으로 연결하는 상담 보조 경험을 더 구체화할 필요가 생겼다. 이 광고 반응은 기간·타깃·예산이 통제된 인과 실험이 아니므로 시장의 확정된 요구가 아닌 **우선 검증할 제품 가설**로 취급한다.
- **제품 방향**: 객관적 학원 정보 기반 탐색·추천은 제품의 기반이자 유지할 핵심 기능이다. 상담 보조 AI는 이를 대체하거나 추천을 축소하는 피벗이 아니라, 사용자가 후보를 상담·비교·판단으로 연결하도록 돕는 핵심 사용 경험이다. 사용자의 상황을 조건과 질문으로 구조화하고, 추천 후보의 근거·미확인 사항을 보이며, 반의 실제 인원·질문 대응 인력·오답 피드백·클리닉·보강 조건 같은 관리 구조를 상담에서 확인하게 한다.
- **정보 층위**: 공개 결과는 (1) 출처·확인일이 있는 **객관적 학원 사실**, (2) 후보를 찾기 위한 런타임 탐색 신호, (3) 공개 리뷰를 탐색해 출처·시점·한계를 남긴 **주관적 경험 근거**, (4) 아직 알 수 없어 상담에서 확인할 점을 구분해 보여 준다. 리뷰는 사실 DB를 덮어쓰거나 단일 품질 판정으로 변환하지 않으며, AI 요약과 근거 메타데이터를 통해 상담 보조와 후보 비교를 보완한다.
- **대기행렬 모형의 지위**: Founder가 제공한 *Determining Optimal Class Size in a Private Academy Using Queuing Theory* 논문은 학생 질문을 질문 수요·질의응답 시간·동시 대응 인력의 관계로 해석하는 근거다. M/M/1·M/M/c는 상담 보조 AI가 `질문 대응 여유`를 설명하고 필요한 질문을 만들기 위한 **내부 보조 모형**으로만 사용한다. 논문 사례의 가동률 임계값과 적정 정원 결과를 모든 학원·과목의 공통 기준으로 쓰지 않는다.
- **명확히 하지 않는 것**: 학원 종합 평점, 교육비 대비 점수, 단일 관리 품질 등급, ‘최적 반 정원’ 판정, 추천 랭킹 가중치로 만들지 않는다. AI는 여전히 학원 품질·학생 상태를 단정하지 않으며, `POST /recommendations/ai`의 `score`를 별점·퍼센트·신뢰도처럼 표시하거나 저장하지 않는다.
- **데이터 경계**: `data/academies/*.json`은 객관적 학원 사실의 유일한 git 정본으로 유지한다. 공개 리뷰와 사용 경험은 별도 DB 경로에서 출처·시점·한계를 가진 주관적 근거로 다룬다. 학원 전체의 `teacher_count`나 `classroom_count`만으로 반별 질문 대응 인력·학생당 강사 수·교육 품질을 추론하지 않는다. 반 단위 운영값은 수집 가능성이 검증될 때에만 별도 운영 프로필을 검토한다.
- **검증 순서**: 먼저 객관적 학원 사실의 범위와 최신성을 계속 보강한다. 동시에 5~10명의 실제 학부모에게 `질문 대응·오답 관리` 상담 질문의 유용성을 검증한다. 이후 공개 리뷰 탐색·근거화의 신뢰성 및 상담·후보 비교 유용성을 검증하고, 그 다음에만 반 단위 운영값의 소규모 수집과 설명형 신호 공개 여부를 검토한다.
- **API·코드 영향**: 이번 결정은 문서·제품 원칙·검증 우선순위의 정렬이다. 현재 `GET /academies`, `POST /recommendations`, `POST /recommendations/ai`, 학원 JSON 스키마, 추천 로직, 공개 UI, 로그인·저장 정책은 변경하지 않는다. 따라서 `docs/api.md`, 데이터 마이그레이션, 코드 변경은 이번 범위에 포함하지 않는다.
- **관련 문서**: [프로젝트 개요](project.md), [데이터 전략](data-strategy.md), [로드맵](roadmap.md), [대기행렬 기반 질문 대응 여유 신호 제안](queueing-management-signal-proposal.md).

## 2026-08-21 — 학원 추천에서 ‘학원·학습 블랙박스 해소’로 첫 MVP를 재정의

- **계기**: 광고 성과와 학부모 상담에서 반복된 문제는 단순한 ‘좋은 학원 찾기’가 아니었다. 바쁜 학부모는 아이가 학원에서 실제로 무엇을 경험하는지, 진도·오답·보강·질문 대응·소통이 어떻게 이루어지는지 직접 확인하기 어렵다. 사춘기 학생과의 정보 비대칭 때문에 강사 상담에 판단을 의존하게 되고, 상담이 충분하지 않으면 계속 다닐지·옮길지의 근거도 부족해진다. 초기 당근 광고에서는 학원비 점검 프레이밍의 클릭률이 일반적인 ‘현재 학원이 최선인가’ 비교 프레이밍보다 높게 관찰됐지만, 기간·타깃·예산 통제가 확인되지 않아 인과로 단정하지 않는다. 이 수치는 외부 카피의 근거로 쓰지 않는다.
- **상위 목표**: 학원콕은 **학부모가 학원과 아이의 학습 상태를 둘러싼 블랙박스를 줄이고, 더 나은 질문과 판단을 하도록 돕는 서비스**다. 불확실성을 없애거나 아이·학원을 판정한다고 약속하지 않고, 이를 확인 가능한 질문·정보·다음 행동으로 바꾼다.
- **첫 공개 MVP**: 하남 미사 고정의 무료 AI 보조 학원 탐색 도구로 둔다. 사용자가 현재 다니는 학원 또는 원하는 조건과 고민을 입력하면 AI가 탐색 조건·상담 질문·추가 확인 항목으로 정리한다. 결과는 출처·확인일이 있는 학원 기본 정보·지도·공개 연락처, 후보로 보인 이유, 아직 확인되지 않은 점을 함께 보여 주고 사용자가 직접 전화·웹사이트·길찾기를 하게 한다. 핵심 흐름은 `상황 입력 → AI 조건/질문 정리 → 후보 정보·지도·근거/미확인 항목 → 사용자 직접 행동`이다.
- **AI와 결과 표현**: AI는 학원 품질이나 아이의 상태를 단정하지 않는다. ‘최고’·‘확정 추천’·‘우리 아이에게 가장 맞음’ 같은 표현을 쓰지 않고, 결과를 **조건과 관련해 확인해 볼 후보 정보**로 표현한다. 데이터가 없는 수업 방식·오답 관리·고등 연계는 추정하지 않고 `상담에서 확인할 점`으로만 표시한다. `score`는 동일 응답 안의 상대 순위이며 별점·퍼센트·신뢰도로 보여 주거나 저장하지 않는다.
- **명시적 제외 범위**: 첫 MVP는 수강 신청, 예약, 결제, 상담 접수 대행, 부모 연락처의 학원 전달, 대가성 결과 순위, 유료 상단 노출, 필수 로그인, 자녀 실명·생년월일·성적표·상세 자유 서술의 기본 수집을 넣지 않는다. 전화·웹사이트·길찾기는 공개 연락처를 보여 주고 사용자가 직접 실행하는 행동이며, 클릭은 비식별 행동 이벤트로만 기록한다. 로그인은 관심 학원 저장 또는 결과 재방문 수요가 검증된 뒤 선택적으로 검토한다.
- **기존 API와 데이터 계약**: `GET /academies`, `POST /recommendations`(하드 필터), `POST /recommendations/ai`(넓은 후보 풀+소프트 랭킹)는 유지한다. 이번 결정은 API를 합치거나 랭킹을 바꾸는 변경이 아니라, 공개 UI가 이를 학원 등록을 중개하는 추천 약속이 아닌 근거 있는 후보 탐색 경로로 표현하도록 정렬하는 변경이다. `data/academies/*.json`의 사실 정본 원칙과 `null`을 미확인으로 남기는 원칙도 유지한다.
- **수익화 순서**: `무료 질문/탐색 MVP → 데이터 신뢰·반복 사용 → 학원 정보 최신화·강화 프로필 수요 검증 → 선택형 상담 예약·리드 연결 검토` 순으로 둔다. 향후 광고·강화 프로필은 명확히 표시하고, 학원의 지불 여부가 일반 후보 순서·AI 근거·추천 논리에 영향을 주면 안 된다. 상담 예약·리드 연결은 명시적 제3자 제공 동의, 운영 기준, 사업자·개인정보·플랫폼 광고 요건을 별도로 검토한 뒤에만 도입한다.
- **당근 광고 운영 게이트**: 제품의 무료 정보 탐색 구조와 당근 유료 광고의 심사 요건은 별개로 관리한다. 광고 재개 전 ‘무료·무결제·무예약·무상담대행·무리드전달’인 랜딩/서비스 URL과 구조를 당근에 제시해 서류·푸터 표기·광고 계정 요건을 서면으로 확인한다. 답변 전에는 유료 웹·앱 광고를 재개하지 않는다.
- **대체 관계**: 과거 문서의 ‘맞춤 추천’은 당시 구현/API·랜딩 이력을 설명하는 기록으로 보존한다. 그러나 이 결정 이후의 공개 제품 정의·카피·신규 기능 우선순위는 이 항목의 블랙박스 해소·질문 우선·후보 탐색 원칙을 따른다.
- **바꾸지 않은 것**: 데이터 정본·출처·확인일·3상태 null 규칙, 두 추천 API의 분리와 투명성 계약, 좌표 응답, 비식별 외부 행동 계측, `/`·`/check`·`/checklists`·`/app`의 현재 배포 상태, 자유 대화형 채팅 및 SSE 미구현 상태. 이번 변경은 문서·지침 정렬이며 화면·API·데이터·광고 집행을 즉시 바꾸지 않는다.

## 2026-08-19 — 메인 준비 중 2칸·예시 복원, 퍼널 크롬 통일

- **계기**: Founder가 방금 만든 메인을 보고 (1) `ServiceRoleSection` 제거 (2) `왜 학원콕인가요?` 3원칙을 준비 중 기능 2칸으로 교체 (3) 삭제했던 서비스 예시 화면 복원을 지시했다. 이어서 모든 소개 페이지 상단을 홈 히어로와 같게 맞추고, 헤더에 운영 전·판매 없음 고지를, 푸터에 카카오 출시 알림을 스크롤과 무관하게 고정하라고 했다.
- **결정**:
  - `/` 섹션 순서: `Hero → SituationSection → PlannedFeaturesSection → ServicePreviewSection → GroundworkSection`. 역할 섹션이 빠져 Hero 다음이 상황 카드다.
  - 준비 중 2칸(`학원 다니기전` / `학원 다니는 중`)은 아직 없는 기능이다. 공개 퍼널에 입력 폼이 없고 학원 속성 필드는 정본에서 0%이며 시기별(1·3·6·12개월) 구조도 코드에 없다. **서술어는 예정형, 배지는 `준비 중`**. 현재형 단정(`추천해드립니다`·`보내드립니다`)은 같은 화면 하단 `정식 출시 후 제공됩니다`와 충돌하고 광고 심사 위험이 있다.
  - 섹션 제목은 `학원콕은 이렇게 도와드립니다` — 아래가 신뢰 원칙이 아니라 기능 예고라 질문형 제목과 어긋난다.
  - `ServicePreviewSection`을 예시 3장으로 복원한다. 익명 표기·`AI 추천 예시` 배지·카드 앞 고지·하단 Disclaimer는 실제 데이터 오인을 막는 장치라 유지한다. 3번째 카드(`□□국어학원`)는 첫 칸의 "3개 학원" 약속과 맞춘다.
  - `/`·`/check`·`/checklists` 화면 히어로는 홈과 동일(`logo-mark` + `HERO_*`). `/check` metadata 제목/설명과 `/checklists` metadata는 페이지 전용으로 남긴다. `/privacy`는 헤더·고정 카카오만, h1은 `개인정보처리방침`. `/app`은 제외.
  - 헤더 로고 옆 텍스트(배지 아님): `현재는 정식 운영 중이 아니고, 소개용 랜딩 페이지입니다. 학원을 중개하거나 수강료를 받지 않습니다.` 헤더·카카오 바는 스크롤과 무관하게 보인다(헤더 `sticky`, 카카오 바 `fixed` — 문서 끝 푸터를 sticky로 올리면 상단에서 안 보인다).

## 2026-07-29 — `PgVectorStore.search()`의 `cosine_distance()` AttributeError 수정

    실행되지 않았다 — 실제로 main 전체 스위트는 이 버그가 있는 채로도 계속
    통과해 왔다. 별도 세션에서 같은 기능(Phase 4b 임베딩/VectorStore)을 중복
    구현하다가 로컬에서 `uv run`으로 실제 provider 환경을 재현해보며 발견했다.
- **조치**: `Review.embedding.op("<=>", return_type=Float)(embedding)`으로 pgvector의
  코사인 거리 연산자를 직접 호출하도록 변경 (`app/providers/pgvector_store.py`).
  우변 바인드 파라미터는 여전히 컬럼과 같은 Variant 타입을 가지므로, 실행 시점에는
  postgres dialect_impl(Vector)의 bind_processor가 정상 적용된다.
- **테스트**: 실 Postgres 없이도 이 버그를 잡을 수 있도록 `tests/test_pgvector_store_query.py`를
  추가 — 가짜 세션(context manager)으로 `search()`를 호출해 거리 표현식을 만드는

## 2026-07-06 — Fact DB 전략 및 스키마 결정
- **제품 전략**: 평가/리뷰 대신 객관적 사실(Fact)만 모으는 DB 우선
  (Phase 1 사실 → Phase 2 AI 요약 → Phase 3 사용자 리뷰, `docs/data-strategy.md`)
  - 이유: 객관성 유지, 학원 항의 리스크 회피, 수집·업데이트 용이. 정확한 DB 자체가 자산
- **3상태 nullable Boolean** (초/중/고, 수업형태, 커리큘럼, 차량): `NULL`=미확인 / `FALSE`=확인됨-없음 / `TRUE`=확인됨-있음
  - 이유: ARRAY 컬럼은 "없음"과 "미확인"을 구분하지 못함 — 이 구분이 "가장 정확한 DB"의 본질.
    부수 효과로 SQLite 테스트 호환 확보. 어휘가 작고 안정적이라 컬럼-값 방식이 저렴
- **data-as-git**: 정본은 `data/academies/*.json`, DB는 멱등 임포터로 재구성되는 파생 저장소. 쓰기 API 없음
  - 이유: PR 리뷰·이력·출처 추적을 git이 제공. 소규모 단일 큐레이터 데이터셋에 적합.
    Phase 3 사용자 리뷰는 예외(DB 직접 쓰기)
- **int autoincrement PK** (UUID 대신): 공개 데이터라 열거 우려 없음, 환경 간 식별은 자연키
  (registration_number, name+address)가 담당
- **수작성 초기 마이그레이션** + `Base.metadata` 네이밍 컨벤션 도입 (테이블 0개인 지금이 무통증 시점)
- **드라이버 스킴 수정**: `postgresql://` → `postgresql+psycopg://`
  - 이유: psycopg v3만 설치되어 있는데 기본 스킴은 psycopg2 dialect로 해석되어 DB 사용 시점에 크래시
- **공공데이터 부트스트랩**: 나이스 학원민원서비스 변환기는 신규 파일 생성 전용
  (기존 파일은 절대 덮어쓰지 않음 — 수동 큐레이션 보호)
